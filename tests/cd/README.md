# 운영 CD 최적화 검증

## 동작

- 태그 배포와 수동 배포 모두 AI·BE를 자동 병렬 배포하고, 두 서비스가 모두 성공하면 FE를 전환한다.
- 별도 체크 항목은 없다. FE 빌드는 기존처럼 ECS 변경 전에 검증하며, FE 전환은 두 서비스가 모두 성공했을 때만 실행한다.
- 릴리스는 새 AI/기존 BE, 기존 AI/새 BE의 API 계약과 DB 마이그레이션 호환성을 유지해야 한다. 2026-10-27 읽기 전용 조회에서 운영 서비스는 각각 desiredCount=2이며 서로 다른 capacity provider를 사용했다. 이것이 향후 용량이나 API 호환성을 보장하지는 않는다.
- 현재 서비스가 안정 상태이고 task definition의 이미지가 요청 digest와 동일하면 새 task definition 등록과 롤아웃을 생략한다. 태그 URI는 동일 digest로 간주하지 않는다.
- 배포 circuit breaker, 롤백 검사, 안정 상태 검사는 유지한다. 병렬 모드에서 한 서비스가 실패해도 다른 서비스의 결과까지 기다린 후 실패한다. 릴리스 전체의 원자적 롤백을 제공하지는 않는다.
- Actions Summary의 ECS 표에 서비스별 `deployed`, `unchanged`, `failed`, 실행 시간과 SHA를 기록한다. 병렬 서비스별 요약을 임시 파일로 분리해 기록 충돌을 방지한다.

## 개선 전후 비교

기존 운영 실행 39597464000, 39723607011의 전체 경과 시간은 각각 16분 10초였다. ECS 단계 합계는 14분 55초, 14분 53초다. 병렬화 예상 약 9분은 추정이며 실제 새 버전 배포로 검증해야 한다.

전체 Actions 경과 시간과 ECS 단계 경과 시간을 구분한다. `unchanged` 배포는 전체 교체 배포와 분리하고, 병렬 모드도 순차 모드와 별도 집계한다. 캐시·이미지 크기·서비스 용량을 기록하고 정상 배포 최소 5건의 중앙값을 비교한다. 실패·롤백도 별도 기록한다.

## 로컬 검증

```sh
bash -n scripts/deploy_prod_services.sh scripts/deploy_ecs_service_prod.sh
python3 -m unittest discover -s tests/cd -v
actionlint .github/workflows/cd.yml
```

테스트는 AWS를 모의 구현으로 대체한다. 동일 이미지 무변경 처리, 불안정 서비스 거부, 병렬 성공, 한쪽 실패 시 양쪽 종료 대기를 확인한다. 실제 ECS 배포 성공을 의미하지 않는다.

## 복구

병렬 실행 문제가 있으면 병렬 배포 도입 전 워크플로로 복원한다. 실패한 ECS 서비스는 기존 circuit breaker 자동 롤백 상태를 확인한다. 동일 이미지 생략을 포함한 최적화 전체를 되돌리려면 이번 변경의 워크플로 및 배포 스크립트를 이전 버전으로 복원한다. 실패한 릴리스에서 FE는 전환하지 않으며, 이미 성공한 다른 ECS 서비스는 자동으로 이전 릴리스로 되돌리지 않는다.


## 개발 CD

원격 main의 cd-dev.yml 및 deploy_ecs_service_dev.sh를 가져와 수정했다.
- 전역 대기열 대신 서비스별 대기열 사용. 자동·수동 배포가 같은 서비스 잠금을 공유하며, 실행 중 배포를 취소하지 않는다.
- 안정 상태의 동일 digest 재배포 생략 및 서비스별 실행 결과/시간 Summary 추가.
- FE는 npm의 기존 캐시를 우선 사용하되 lint/build 검증 유지.
- 개발 BE 로드밸런서: 연결 종료 대기는 기존 300초 유지, health check interval 30→10초, healthy threshold 5→2. 2026-10-27 AWS에 적용하고 확인했다. 신규 타깃은 첫 성공 검사로 healthy가 되므로 threshold 변경을 단순히 시작 시간 절감으로 계산하지 않는다.
- AI 스트리밍 연결의 종료 대기, 운영 로드밸런서, ECS 기동 유예 시간은 유지한다. 연결 종료 대기는 실제 장기 요청 처리 시간을 측정한 뒤 조정한다.
- 헬스체크 설정 복구가 필요하면 개발 BE 타깃 그룹의 주기를 30초, 정상 판정 기준을 5회로 변경한다. 연결 종료 대기는 300초를 유지한다.
- 연결 종료 대기를 120초로 줄였던 변경은 요청 시간 근거가 부족하여 300초로 복원했다. 실제 절감 시간은 다음 배포에서 확인해야 한다. 동일 이미지 생략 건은 별도 집계한다.

## 최종 검토

- 운영 FE 빌드 Node.js를 개발 CD·FE CI와 같은 24로 통일했다.
- 운영 릴리스 태그는 출력 전에 형식을 검사하고 환경변수로 검증 스크립트에 전달한다.
- 실행 수가 0인 서비스를 정상 배포로 간주하지 않는다. 개발 CD는 현재 PRIMARY task definition까지 확인한 뒤 배포·생략한다.
- 오프라인 테스트 11개 통과: 양쪽 병렬 실패 전파, 변경 이미지 실제 갱신 경로, 롤아웃 실패·롤백 실패 처리, 실행 수 0 거부 등을 포함한다. 워크플로 2개 actionlint, 셸 구문, diff 공백 검사도 통과했다.
- 개발 FE는 기존 Actions 단계 시간으로 측정하며, 개발 ECS는 배포 스크립트 시간만 Summary에 기록한다. 운영 Summary의 job 시간은 첫 타이머 단계부터이며 큐·승인 대기는 포함하지 않는다. 전체 경과 시간과 혼동하지 않는다.
- 기존 전역 잠금과 새 서비스별 잠금은 서로 조정되지 않으므로, 전환 시 기존 개발 배포가 모두 종료된 상태에서 새 워크플로를 반영한다.
- 병렬 배포의 혼합 버전 API·DB 호환성 및 실제 AWS 롤아웃은 이 오프라인 테스트로 검증하지 않았다. 운영 릴리스 전 별도 확인이 필요하다.
- 동일 digest여도 환경변수·시크릿 갱신을 위한 강제 재기동이 필요한 경우에는 이 이미지 배포 경로의 생략 동작을 고려해야 한다. 설정 배포·강제 재기동 절차는 별도 개선 대상이다.

추가 최적화 우선순위: 개발 ECS의 이미지 pull·프로세스 기동·헬스체크·드레이닝 시간을 분리 측정 → 실제 병목에 맞춰 이미지 크기/기동을 개선. FE 산출물 재사용은 환경변수와 release base 경로가 같을 때만 적용한다. 연결 종료 대기 축소는 장기 요청 처리 시간 근거가 확보되기 전에는 적용하지 않는다.


## 코드 정리

- 개발 ECS 배포는 자동·수동 입력을 service/SHA 목록으로 정규화한 뒤 하나의 matrix 작업으로 실행한다. SHA가 없는 서비스는 목록에서 제외한다. frontend 이벤트에는 ECS 작업을 실행하지 않는다.
- matrix의 fail-fast=false와 서비스별 잠금을 유지한다. 한 서비스 실패로 다른 서비스의 진행 중 배포를 취소하지 않는다.
- 운영 배포에서 사용하지 않는 순차/병렬 선택 인수와 순차 실행 분기를 제거했다.
- 기존 EC2·Compose 배포 코드와 개발/운영 ECS 스크립트 분리는 유지한다.
